# Physical plaque placement — the 4 site tracking targets

Audience: whoever is physically printing and mounting the 4 tracking
plaques on the site model (or a desk/bench proxy for testing before the
real model exists). This is the "where exactly do these go" companion to
`docs/asset-authoring-guide.md` §3.5, which has the underlying derivation;
this doc exists because that derivation was spread across a script, a
manifest, and a table — this pulls it into one operational checklist. It
did not exist before 2026-08-14.

**Read this whole doc before printing/mounting anything** — in particular
§4 (what's real vs. still placeholder), since that changes what "exact
measurement" means right now.

**REQUIREMENT — mounting tilt (confirmed 2026-08-17, coworker physical
review, unaffected by every artwork/size change since): every plaque
mounts FLAT on its ledge strip, artwork facing UP toward the camera —
never standing vertically like a museum placard.** This is not a
default or a convenience — `ImageTargetAnchorSource.ts`'s
`TARGET_FRAME_TO_WORLD_FIX` is written specifically for a flat, table-lying
marker (reasoning from this project's own already-validated MindAR glue
for the identical physical shape); mounting any plaque vertically will
track against the wrong axis convention and place content wrong. Full
detail in §2 and §5.

**2026-08-25 artwork swap:** the production `'site'` entry's 4 tracking
targets are no longer the QR plaques this doc originally described —
see §1. The mount POSITIONS (§2's table) and the flat-mount requirement
above are unaffected (same ledge footprint); only the printed artwork
and its size changed.

## 1. What gets printed

**Current production artwork (2026-08-25 swap):** four **visually
distinct** abstract Voronoi tracking targets —
`tools/plaque/site-tracking/tracking-{front,back,left,right}.png` —
generated by `tools/build_site_tracking_targets.py`, laid out for
printing by `tools/plaque/site-tracking/print-sheet.html`. Open that HTML
file in a browser and print it; it includes a 100mm calibration ruler
printed alongside the targets specifically so you can verify your printer
didn't rescale the page (measure the ruler with an actual ruler before
trusting the target size).

| Property | Value |
|---|---:|
| Target size (each) | 30 × 30 mm (square) |
| Artwork resolution | 720 × 720 px (24px/mm) |
| Content | independent-seed black/white Voronoi cell pattern per side, no QR, no shared regions between sides |

**Why this replaced the earlier QR-plaque design** (§1 below the table
described until 2026-08-25): on-device testing of the QR plaques showed
slow acquisition, wrong initial pose, and continuous jitter — traced to
the QR module grid being a repeating pattern, and (since all 4 old
plaques encoded the same URL) pixel-identical across all 4 "distinct"
plaques, violating both this project's own tracking-artwork guidance
(`docs/asset-authoring-guide.md` §3.1) and 8th Wall's own. Session
bootstrap (the QR code, "open the web app") and pose tracking (the image
target) were deliberately decoupled — the QR code is now a signage
concern, off the ledge entirely, no longer part of the tracked scene.
Full reasoning: AR_SYSTEM.md §G's 2026-08-25 Phase 6 entry,
`docs/research/8th-wall-troubleshooting.md` §22.

A small side label (FRONT/BACK/LEFT/RIGHT) is stamped in one corner of
each target — both for installer verification and as the orientation
cue now that the shape is square (a landscape plaque's own aspect ratio
used to make a 90°-mounting mistake obvious on its own; legible text
serves the same purpose here — upside-down/sideways text is obviously
wrong to a human at a glance).

All 4 targets are visually and structurally independent (no shared QR
payload at all now) — which physical side is in view is resolved
entirely by image recognition at runtime (§A), same as before.

**Retired, kept only as a MindAR validation harness, not printed for the
production model anymore:** the original 90×30mm QR-plaque design
(`tools/plaque/site/plaque-{front,back,left,right}.png`,
`tools/build_site_plaques.py`, `tools/plaque/site/print-sheet.html`) —
still wired to the single-plaque `site-front`/`site-back`/`site-left`/
`site-right` manifest entries (§6), never the production `'site'` entry.
Don't print this set for the real model; it's superseded artwork kept
only for that harness.

## 2. Where each plaque goes — the reference frame

The model's own origin (0, 0, 0) is a **fixed corner of the terrain
footprint**, not a plaque center (§A's four-plaque amendment). Looking
down at the model from above, with FRONT facing you:

```
                         BACK ledge
              ┌──────────────────────────────┐
              │                               │
     LEFT     │                               │    RIGHT
     ledge    │         terrain footprint     │    ledge
              │      1606.55mm × 1343.03mm    │
              │                               │
              └──────────────────────────────┘
          (0,0) — origin corner    FRONT ledge
```

- **Origin (0,0)** sits at the corner where the LEFT edge and the FRONT
  edge of the terrain meet.
- **X** increases toward the RIGHT edge (0 → 1606.55mm).
- **Z** increases toward the BACK edge (0 → 1343.03mm).
- The ledge is a uniform-width border running around all 4 sides,
  outside the terrain footprint — **width confirmed 2026-08-18: 3.5cm,
  real measurement, uniform on all 4 sides, no longer placeholder** (§4).
  The full baseboard (terrain + ledge on all sides) is 1675 × 1414 mm,
  also a real measurement now, not derived from the ledge width — the two
  independently agree to within ~1.5mm.

**Plaque centers**, measured from the origin corner, along the model's own
X/Z axes (i.e. "X mm from the left edge, Z mm from the front edge" —
these are the exact values `manifest.ts`'s `'site'` entry uses).
**Computed 2026-08-18** against the real ledge width and the (then-current)
90×30mm QR-plaque size; **unchanged by the 2026-08-25 artwork swap to the
30×30mm targets in §1** — the swap moved none of the mount footprint,
only which artwork prints at each of the same 4 points (AR_SYSTEM.md §G,
`manifest.ts`'s `'site'` entry comment):

| Side | X from origin | Z from origin | Sits on |
|---|---:|---:|---|
| front | 803.275 mm | 20.488 mm | front ledge strip, flush with the outer board edge, centered along its length |
| back | 803.275 mm | −1363.513 mm | back ledge strip, flush with the outer board edge, centered along its length |
| left | −19.225 mm | −671.513 mm | left ledge strip, flush with the outer board edge, centered along its length |
| right | 1625.775 mm | −671.513 mm | right ledge strip, flush with the outer board edge, centered along its length |

Each plaque's center sits **outside the terrain footprint**, flush with
the true outer edge of the baseboard (its outer half at the board
boundary, inner half extending onto the ledge — the current 30×30mm
square target is smaller than the 35mm ledge on every axis, so it can't
overhang either the board edge or the terrain no matter how it's
rotated in-plane, unlike the old 90×30mm landscape plaque which only
avoided overhang along its 30mm short axis). front/back are centered
along the model's X-width (803.275mm ≈ half of 1606.55mm); left/right
are centered along its Z-depth (671.513mm ≈ half of 1343.03mm, sign
flipped from the pre-2026-08-18 table because the model's own `v`-axis
convention was corrected that same day — see AR_SYSTEM.md §G).

**Mounting tilt — REQUIREMENT, confirmed 2026-08-17, coworker physical
review, unaffected by the 2026-08-25 artwork swap:** each target lies
**flat** on its ledge strip, artwork facing **up** (toward the
ceiling/camera), the same way the physical model's terrain and the
Blender placeholder plaque markers already sit — NOT standing vertically
like a museum placard, which was the earlier (incorrect) assumption.
`rotationYawDeg` in the manifest is unaffected by this: it only corrects
which of the 4 horizontal directions each target's artwork "reads" toward
(front=0°, back=180°, left=90°, right=−90° — purely a function of which
edge of the terrain rectangle the target sits on, not its tilt). The
tracking glue in `ImageTargetAnchorSource.ts` (`TARGET_FRAME_TO_WORLD_FIX`)
IS affected by tilt — see §5 for the current value and confidence level.

**Mounting rotation — which way each target reads (confirmed 2026-08-17
against a reference diagram; the "up" definition below transfers
unchanged to the 2026-08-25 artwork — see the note after the table):**
orient each target so its content reads right-side-up to someone standing
at that edge, outside the model, and looking inward toward the terrain —
the same way a trailhead sign reads correctly as you walk up to it.
Equivalently and exactly: **each target's "up" points straight at the
terrain's center**, not away from it:

| Side | "Up" points toward | I.e. |
|---|---|---|
| front | terrain center (north) | away from the front edge, into the model |
| back | terrain center (south) | away from the back edge, into the model |
| left | terrain center (east) | away from the left edge, into the model |
| right | terrain center (west) | away from the right edge, into the model |

**On the 2026-08-25 artwork specifically:** each target's FRONT/BACK/
LEFT/RIGHT corner label (`add_side_label()`,
`tools/build_site_tracking_targets.py`) sits in the artwork's bottom-left
corner, legible left-to-right when the target is held right-side-up —
mount so that label reads normally (not upside-down or sideways), which
is exactly the "up points at the terrain center" rule above applied to
this artwork.

This was genuinely unspecified before — the tilt fix above only ever
addressed flat-vs-vertical, never this in-plane rotation. No manifest or
code change needed for this: `rotationYawDeg`'s 0°/180°/90°/−90° pattern
is a set of *relative* corrections between the 4 plaques (front defines
the 0° reference), so it stays correct regardless of which absolute
direction "front" itself reads toward — this is purely a physical
mounting instruction, not a software one.

## 3. Step by step

1. Print `tools/plaque/site-tracking/print-sheet.html` (§1 — NOT
   `tools/plaque/site/print-sheet.html`, that's the retired QR-plaque
   sheet). Verify the 100mm calibration bar with a real ruler before
   trusting anything else on the page.
2. Cut out the 4 targets.
3. Identify the origin corner on the physical model: the corner where the
   left and front edges of the terrain meet (§2's diagram).
4. Measure and mark the 4 center points from §2's table along the ledge
   (not the terrain — the ledge is the border strip outside it).
5. **Mount each target FLAT at its marked point, artwork facing up** —
   this is a requirement, not a style choice (§2's "Mounting tilt") —
   rotated so its FRONT/BACK/LEFT/RIGHT corner label reads right-side-up
   standing at that edge and facing into the model — i.e. "up" points at
   the terrain center (§2).
6. Confirm each target's own corner label (FRONT/BACK/LEFT/RIGHT) matches
   the position you're mounting it at — don't rely on the Voronoi pattern
   itself to tell them apart by eye, read the label (a mismatch would
   make 2 targets scan-ambiguous).
7. Test each target independently before considering the model "ready" —
   see §6.

regenerated GLB, cross-checked against the GLB's own binary data) — then
update both that table and this doc's §2.

## 5. Tracking math this placement feeds — current confidence

Once physically mounted, each plaque's tracked pose is composed with its
own `originOffsetMeters` (§2's table, in meters) and `rotationYawDeg`
(derived from which edge it sits on — front=0°, back=180°, left=90°,
right=−90°) in `ImageTargetAnchorSource.ts`, so scanning any one of the 4
plaques anchors the SAME site-scene at the SAME real-world position and
orientation (§A/§E "Multi-target plaques").

**Confirmed by software tests** (`ImageTargetAnchorSource.test.ts`): the
composition math itself is internally consistent — all 4 targets recover
the same assumed world placement from their own simulated tracked event.

**Two runtime fixes landed 2026-08-26, both software-verified, both
still needing an on-device pass against real printed targets:**
- **A real bug in the multi-target switching logic, found and fixed.**
  Previously, once any one plaque acquired the anchor, scanning any of
  the OTHER three plaques for the first time was silently rejected
  unless a sample happened to land exactly when 8th Wall's
  `trackingStatus` was `NORMAL` — the code held a brand-new plaque's
  first sighting to the same strict re-detection gate meant for noisy
  re-detection of the SAME already-anchored plaque. This is the leading
  software-side explanation for "only one of the 4 targets worked" on a
  prior physical test. Fixed: a plaque's first-ever sighting now applies
  unconditionally, the same as the anchor's very first-ever sample.
- **Pose smoothing, previously proposed and deliberately left
  unimplemented, now implemented.** `ImageTargetAnchorSource.applyPose()`
  now runs every trustworthy sample through a One Euro filter (tuned
  like MindAR's own `TRACKING_PROFILE_RIGID_ANCHOR` — high beta, so it
  gets out of the way during real camera motion and only damps at-rest
  tremor), instead of applying every raw tracked sample directly. Filter
  state resets on every plaque switch or re-detection, so a discontinuity
  still snaps rather than smoothing across it. Addresses the
  visible-spin/scale jitter reported testing the single-target
  `site-tracking-front` harness.

**Corrected 2026-08-14 against external evidence** (for a since-superseded
vertical-mount assumption), **then corrected again 2026-08-17** once the
mount orientation itself was confirmed flat: `TARGET_FRAME_TO_WORLD_FIX`
is back to a 90°-rotation (`Rx(+90°)`), reasoning from this project's own
already-validated MindAR glue for the identical physical shape (a flat,
table-lying plaque — `SceneGraphLoader.ts`'s
`GLTF_TO_MINDAR_ROTATION_X_RADIANS`), not a blind revert to the pre-2026-08-14
value. See `docs/research/8th-wall-troubleshooting.md` §14 for the
original evidence trail and its follow-up entry for this correction.

**Still genuinely unverified, requiring the real physical mount from this
doc, not software:** whether 8th Wall's own image-target rotation
convention for a flat marker actually matches MindAR's — the reasoning
above is a strong same-project precedent, not an on-device 8th Wall
confirmation. `rotationYawDeg` is NOT in question (§2 — it's orthogonal to
mount tilt).

**2026-08-18: `originOffsetMeters`/`physicalTargetWidthMeters` recomputed
against the real ledge width and the redesigned 90×30mm plaque** (§2/§4)
— `public/assets/site-scene.glb`/`.usdz` and the compiled image-target
JSON for all 4 plaques were resynced/recompiled in the same pass, so the
live `'site'` manifest entry is internally consistent again. This is a
geometry/size update only — none of it touches the tracking math's own
confidence level above.

## 6. Testing a single plaque before the full model exists

Two ways, depending on what you're checking:

- **Testing tracking/content in isolation, no physical terrain needed
  yet:** use one of the single-plaque MindAR harness entries
  (`site-front`/`site-back`/`site-left`/`site-right` in `manifest.ts`) —
  each anchors the FULL digital scene centered on whichever single plaque
  is scanned (not the shared-corner offsets above), so it doesn't need
  the real model to look "correct" for a tracking/content sanity check.
  These are MindAR, not 8th Wall — a validation harness only, never the
  production path (AR_SYSTEM.md §G).
- **Testing the real production experience** (`'site'`, 8th Wall,
  shared-corner offsets): scanning any one plaque in isolation, without
  the physical terrain and the other 3 plaques actually in place at
  their real relative positions, will correctly place content at its
  REAL metric offset from that plaque — which, without the terrain there
  to overlay onto, will look "far away" or "off to the side" on a small
  test surface (the offsets in §2's table are 0.7–1.6 meters, real
  architectural scale, not a small-object scale). That's the expected
  consequence of testing real-world-scale positioning without the real
  model present, not a rendering bug — it needs either the actual
  fabricated model, or a full-scale mockup of the terrain footprint
  (§2's dimensions), to look "correct" the way it will once the physical
  model exists.
